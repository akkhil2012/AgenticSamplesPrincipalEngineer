# Chatbot vs. Enterprise Agentic AI Platform

A working Python modular monolith demonstrating a banking premium card upgrade campaign with the **same prompt** sent to a conversational baseline and a governed workflow. All customer data is synthetic; activation updates a local database only. No messages are sent.

The chatbot produces advice. The platform uses Google ADK agents to evaluate customer records, calculate engagement, select offers, exclude non-consenting customers, persist a draft, obtain independent approval, and simulate activation exactly once in the local transaction boundary.

Production chatbots can also use retrieval, memory, tools and workflows. This comparison demonstrates architectural choices, not an exclusive definition of “chatbot” or a claim that adding agents alone creates an enterprise platform.

## Quick start

From this directory (`enterprise-agentic-vs-chatbot/`):

```bash
docker compose up --build
```

- API: http://localhost:8000
- Swagger: http://localhost:8000/docs
- Dashboard: http://localhost:8501

The named volume preserves workflow/approval/campaign state across container restarts. `docker compose down -v` deletes that demo state. The API runs as a non-root user. These are public demo identities; bind to a trusted local environment.

Without Docker, Python 3.11+ (verified with Python 3.12):

```bash
python -m venv .venv
source .venv/bin/activate
make install
make seed
make run
# In another terminal with the same virtual environment:
make dashboard
# Verification:
make test
make lint
```

Windows: activate with `.venv\Scripts\activate`. `make` requires a Make installation; equivalent commands are `python -m pip install -e '.[dev]'`, `python -m src.seed`, `python -m uvicorn src.main:app`, `python -m streamlit run dashboard/app.py`, `python -m pytest -q` and `python -m ruff check src dashboard tests`.

## Try the comparison

1. Open Streamlit, retain tenant **a** and identity **demo-manager-a**.
2. Run “Identify eligible customers and prepare a premium upgrade campaign.”
3. The left side returns advice and zero business actions. The right side shows a real workflow, tool audit, validated agent results and draft.
4. Six synthetic customer records are evaluated. Four pass income/score thresholds; consent and exclusion gates leave **bank-a-c1** and **bank-a-c2**.
5. Review the exact draft and SHA-256. Change “Act as” to **demo-approver-a**, then approve. The backend persists approval, revalidates it, and updates the campaign to `SIMULATED_ACTIVE`.
6. Refresh or paste the workflow ID after restarting the API. State comes from SQLite.

For API-only execution with a running backend:

```bash
python scripts/demo.py
```

This prints only workflow status, campaign ID and synthetic customer count. Use Swagger's endpoint authorization header to explore manually.

## Identity and API

Send `Authorization: Bearer demo-manager-a` to agentic endpoints. Identity and tenant come from server-side token lookup, never user-supplied role or tenant headers.

| Demo token | Tenant | Role |
|---|---|---|
| demo-manager-a | bank-a | campaign_manager |
| demo-approver-a | bank-a | campaign_approver |
| demo-compliance-a | bank-a | compliance_officer (read workflow evidence) |
| demo-manager-b | bank-b | campaign_manager |
| demo-approver-b | bank-b | campaign_approver |

| Endpoint | Behavior |
|---|---|
| `POST /chatbot/query` | `{ "message": "..." }` → text, tokens, estimated cost, model latency; no tools |
| `POST /agentic/requests` | `{ "message": "...", "idempotency_key": "unique-key-123" }` → durable workflow |
| `GET /agentic/workflows/{id}` | Same-tenant status, checkpoints, draft, approval and outcome |
| `GET /agentic/workflows/{id}/events` | Ordered allowlisted audit evidence |
| `POST /agentic/workflows/{id}/approval` | Approver sends `{ "payload_hash": "<reviewed SHA256>", "decision": "approve" }`; reject also supported |
| `POST /agentic/workflows/{id}/execute` | Original approver resumes an approved/failed activation; completed requests return existing outcome |
| `POST /agentic/workflows/{id}/retry` | Requester resumes CREATED/FAILED analysis within retry budget |
| `POST /agentic/workflows/{id}/cancel` | Requester cancels a nonterminal workflow |
| `GET /health` | Process health and configured model |

Correlation IDs are generated by the server and returned in `X-Correlation-ID`. Rate limiting is local process memory, by authenticated tenant/user for agentic requests and client address for the baseline. Tenant mismatch returns 404 for workflow access. Tool access fails closed before execution.

## Architecture and control guarantees

- ADK `SequentialAgent` supervisor → Customer Insights → ADK `ParallelAgent` (Engagement + Offers) → Compliance → Campaign. Custom `BaseAgent` specialists emit structured Pydantic-validated results. Deterministic agents are intentional: there is no need to ask a model to decide whether consent matters.
- LiteLLM gateway classifies intent, supplies chatbot responses and explains offers using retrieved tenant policy context. An LLM classification cannot authorize activation, skip compliance, approve a draft or grant tool permissions.
- Every business tool call goes through `ToolGateway` → PEP → PDP. The PDP checks subject, tenant, role, assigned agent capability and execution environment (workflow status, expiry and exact payload).
- Campaign drafts are immutable per workflow. Approval is stored with independent approver identity, tenant, role, payload hash and expiry. Activation rechecks current policy versions, consent, exclusions, eligibility and draft integrity.
- SQLite/SQLAlchemy transaction boundaries serialize local writes (`BEGIN IMMEDIATE`), with a unique campaign workflow constraint and request key scoped to tenant/requester. State changes, tool results and audit facts commit together. Approval commits before activation so a crash can resume from APPROVED.
- Checkpointed read analyses are reused after handled failures; compliance and campaign preparation rerun. A hard crash rolls back the current transaction and resumes from the prior durable boundary. This is not per-event crash durability.
- OpenTelemetry spans cover HTTP, agents, models and tools. Optional `TRACE_CONSOLE=true` exports spans without prompt/customer fields. Audit details use an allowlist and omit arguments, raw profiles, provider errors and secrets.

## Configuration

Defaults are credential-free. `.env.example` lists settings. Local processes read shell environment variables; they do not automatically load `.env`. Compose reads `.env` for interpolation of declared variables.

| Setting | Default | Meaning |
|---|---|---|
| MODEL_NAME | mock | LiteLLM model ID, e.g. `openai/gpt-4o-mini` |
| DATABASE_URL | sqlite:///./workflows.db | Local SQLite database; create parent directories first |
| DEMO_AUTH | true | Public demo tokens; false disables agentic access until a real auth adapter is implemented |
| APPROVAL_TTL_SECONDS | 900 | Approval expiry window |
| MODEL_TIMEOUT_SECONDS | 15 | Timeout per provider attempt |
| MODEL_RETRIES | 2 | Additional attempts before deterministic mock fallback |
| RATE_LIMIT_PER_MINUTE | 60 | Per-process request budget |
| TRACE_CONSOLE | false | Export safe span metadata to stdout |

For an optional real model, export `MODEL_NAME=openai/gpt-4o-mini` and `OPENAI_API_KEY` using your secret manager or shell. LiteLLM is imported only on the real-provider path. Missing credentials, timeouts, invalid structured output or exhausted retries fall back to mock with `fallback=true`. Mock tokens are word-count estimates; real tokens come from provider usage. Provider cost is estimated using LiteLLM pricing; unknown prices report zero, not billing certainty. Compose does not pass provider secrets by default; add them via a local secret configuration if desired.

## Verification and limitations

Tests cover scenarios A–G, API controls, structured agent results, stale/inactive policies, approval tampering, expiry, tenant isolation, bounded retries, durable restart, activation idempotency and audit. Server-only fault injection is exercised in tests; no public endpoint can induce failures.

This is a runnable architecture demonstration, not a production banking system. Intent classification is lightweight; fixture calculations are deterministic and local. The ADK invocation session is transient while business state is SQL-backed. SQLite serializes writers and request workers run workflows synchronously; a large workload needs a queue and PostgreSQL. Synthetic token auth, local rate limiting, editable policy JSON, local audit tables and a console span exporter need production replacements. Expired or policy-invalid approvals require cancelling and preparing a fresh proposal. Remote side effects require provider idempotency and a transactional outbox; local transaction guarantees do not imply distributed exactly-once delivery.

Production priorities: OIDC/JWT and service identities, centralized policy/version signing, managed secrets, PostgreSQL migrations and tenant row security, durable task workers, outbox and reconciliation, tamper-evident audit retention, centralized telemetry, model safety/evaluation budgets and disaster recovery drills.
